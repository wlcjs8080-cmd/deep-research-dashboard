# 세션 시작 절차

사용자가 새 작업 세션을 시작하면 에이전트는 아래 순서를 따르라:

1. .cursor/rules/ 안의 3개 RULE.md를 모두 읽는다 (alwaysApply: true이므로 자동 로드됨)
2. project-context/RULE.md의 "현재 상태"와 "다음 작업 목록"을 확인한다
3. 사용자가 "현재 상태 요약해줘" 또는 "다음 작업 뭐야"라고 물으면 즉시 답변한다
4. 사용자가 작업 지시를 하면, 다음 작업 목록의 우선순위를 참고하여 진행한다


# 세션 종료 절차

사용자가 작업을 마치거나 "오늘 작업 정리해줘"라고 하면:

1. 이번 세션에서 완료한 작업을 요약한다
2. project-context/RULE.md의 "세션 히스토리"에 새 세션 기록을 추가한다
3. project-context/RULE.md의 "현재 상태"를 최신으로 업데이트한다
4. project-context/RULE.md의 "다음 작업 목록"에서 완료 항목에 ✅ 표시한다
5. 작업 중 발견된 코딩 교훈이 있으면 coding-standards/RULE.md에 추가한다
6. 작업 중 발견된 절차 규칙이 있으면 이 파일(workflow/RULE.md)에 추가한다


# RULE.md 업데이트 규칙

에이전트가 RULE.md 파일을 수정할 때 반드시 지킬 것:

- 기존 내용을 절대 삭제하지 마라. 추가만 하라.
- 한 번에 한 파일만 수정하라. 동시에 여러 RULE.md를 수정하지 마라.
- 수정 전에 해당 파일의 현재 내용을 먼저 읽어서 구조를 파악하라.
- 수정 후 사용자에게 "X 파일의 Y 섹션에 Z 내용을 추가했습니다"라고 보고하라.
- 사용자가 "알맞은 RULE.md에 추가해줘"라고 하면:
  1. 3개 RULE.md의 역할 설명을 비교한다
  2. 가장 적합한 파일을 판단한다
  3. 해당 파일의 맞는 섹션에 추가한다
  4. 어디에 추가했는지 사용자에게 알려준다


# git 절차

커밋 전 필수 확인:
- git add 전에 반드시 git status 명령어로 secrets.toml이 포함되지 않는지 확인
- .streamlit/secrets.toml이 목록에 보이면 절대 add하지 마라
- .gitignore에 .streamlit/secrets.toml 줄이 있는지 확인

일반적인 커밋-푸시 흐름 (한 줄씩 순서대로 실행):
- 1단계: git status (secrets.toml 미포함 확인)
- 2단계: git add -A
- 3단계: git commit -m "커밋 메시지"
- 4단계: git push origin main

커밋 메시지 규칙:
- 한국어로 작성
- 무엇을 했는지 구체적으로 (예: "12개 항목 체계 재구성 + MU 테스트 통과")
- 변경 파일이 여러 개면 주요 변경 위주로 요약

API 키 노출 사고 시 대응:
- 1. 즉시 해당 API 제공자 사이트에서 키 재발급
- 2. secrets.toml에 새 키 입력
- 3. .gitignore 확인
- 4. GitHub 저장소에서 해당 커밋 히스토리 확인


# 배포 흐름

전체 흐름:
Cursor에서 코드 수정 → git push origin main → Streamlit Cloud 자동 반영

Streamlit Cloud 주의사항:
- secrets.toml은 Streamlit Cloud 대시보드에서 별도 설정 (Settings → Secrets에 직접 입력)
- requirements.txt에 없는 패키지는 배포 시 설치 안 됨
- 새 패키지 추가 시 반드시 requirements.txt 업데이트 후 push
- 배포 후 오류 발생 시 Streamlit Cloud 대시보드의 로그 확인


# 터미널 명령어 안내 규칙

에이전트가 사용자에게 터미널 명령어를 안내할 때:

- 여러 줄 명령어는 반드시 "한 줄씩 엔터"인지 "한번에 복붙 가능"인지 표시하라
- PowerShell 환경임을 항상 고려하라 (이 프로젝트의 기본 터미널)
  - code 명령어 사용 불가
  - 파일 생성은 New-Item 사용
  - 디렉토리 생성은 mkdir -p 사용 가능
- 명령어가 3줄 이상이면 번호를 매겨라
- 위험한 명령어(삭제, 덮어쓰기)는 실행 전 경고하라


# secrets.toml 보안 규칙

- secrets.toml의 실제 키 값은 채팅에서 절대 출력하지 마라
- secrets.toml의 구조(섹션명, 키 이름)는 안내 가능하지만 값은 "..." 으로 마스킹
- 사용자가 키 값을 채팅에 붙여넣으면 "키가 노출되었으니 주의하세요"라고 알려라
- GitHub에 push 전 .gitignore 확인을 항상 상기시켜라


# 파일 수정 안전 규칙

app.py 수정 시:
- app.py는 단일 파일에 전체 로직이 있으므로, 수정 범위를 최소화하라
- 함수 단위로 수정하고, 수정하지 않는 함수는 건드리지 마라
- 대규모 리팩토링은 사용자 승인 후에만 진행하라
- 수정 전에 어떤 함수를 수정할 것인지 먼저 알려라

requirements.txt 수정 시:
- 새 패키지 추가 시 버전 번호는 명시하지 마라 (최신 버전 자동 설치)
- 불필요한 패키지는 추가하지 마라
- 추가 후 반드시 사용자에게 "requirements.txt에 X 패키지를 추가했습니다" 보고


# 테스트/검증 절차

코드 수정 후 로컬 테스트:
- streamlit run app.py 명령어로 실행
- 브라우저에서 티커(예: AAPL, NVDA, MU) 입력해 분석 실행
- 에러 없이 12개 항목이 모두 출력되는지 확인

배포 전 체크리스트:
- 1. 로컬 테스트 통과
- 2. git status로 secrets.toml 미포함 확인
- 3. requirements.txt에 새 패키지 반영 여부 확인
- 4. git push 후 Streamlit Cloud 대시보드에서 빌드 성공 확인


# 사용자와의 소통 규칙

- 사용자는 바이브 코딩 초보 수준이다. 전문 용어를 쓸 때는 한 줄 설명을 함께 붙여라.
- 코드 변경 사항을 설명할 때 "왜 바꾸는지"를 먼저 말하고 "어떻게 바꾸는지"를 말하라.
- 한 번에 여러 파일을 동시에 수정하지 마라. 한 파일씩 수정하고 확인받아라.
- 에러가 발생하면 에러 메시지의 핵심을 한국어로 번역해서 설명하라.
- "이거 왜 안 돼?" 같은 질문에는 원인을 먼저 말하고, 해결 방법을 바로 제시하라.
